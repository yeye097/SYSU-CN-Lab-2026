# Lab2 Web 缓存代理 — 项目开发指导路线

> 依据：《Web 缓存代理实验分工与接口方案》（`架构.docx`）与《2.Web缓存实验》（实验要求）。
> 本文给出完成本项目的**统一路线**：先划分阶段，再按顺序列出 A、B、C 每人的完成步骤。所有接口以架构文档为准，本文只规定"谁、按什么顺序、做什么、交付什么"。

## 一、项目总览

**目标**：实现支持多客户端并发的 HTTP GET 缓存代理（不含 HTTPS/CONNECT），完成缓存命中、过期验证、内容更新、容量管理及异常处理，整合为独立可运行软件，并完成 Wireshark 抓包分析与实验报告。

**分工**：

| 成员 | 负责文件 | 职责 |
| :--- | :--- | :--- |
| A | `proxy_server.py` + 公共文件（`http_types.py`、`config.py`） | 监听与并发、客户端请求解析、调用缓存控制器、发送响应、错误响应、连接清理；启动入口和配置；**代码集成** |
| B | `cache_controller.py`、`cache_store.py` | 缓存决策、新鲜度、条件验证、更新、LRU 淘汰、并发保护；**报告最终合并** |
| C | `origin_client.py`、`mock_origin_server.py`、`traffic_generator.py` | 源站请求与响应解析、超时处理、可控测试源站；**Wireshark 抓包与抓包分析章节** |

**请求处理流向**：客户端 → A（接入）→ B（缓存控制）→ 必要时 C（访问源站）→ 逐层返回。

**阶段 0 必做事项**（不定就无法并行）：

1. 确认 `http_types.py`：`HTTPRequest`（method/url/host/port/path/headers）、`HTTPResponse`（status_code/reason/headers/body）、`CacheEntry`；headers 用 `list[tuple[str,str]]` 不区分大小写查找；
2. 确认四个签名：`read_client_request(sock)`、`CacheController.handle(request)`、`OriginClient.fetch(request, conditional_headers=None)`、`write_client_response(sock, response)`；
3. 确认 **B 通过构造参数接收 `OriginClient`**（便于单测替换模拟对象）；
4. 确认统一异常类型与"A 映射 400/502/504、C 只抛异常不合成错误响应"的边界；
5. 确认日志统一格式（含请求编号、URL、HIT/MISS/REVALIDATE/BYPASS 标记）；
6. 确认 C 的测试源站路径清单与首部约定（`/index.html`、`/chunked`、`/eof`、`/update`、`/reset`、`/delay`、`/status`，端口 8000）。

### 阶段 0 决策机制（A 定稿，B、C 直接开工）

| :--- | :--- | :--- |

**运转规则**：

1. A 在阶段 0 一次性定好全部内容并贴出：`http_types.py`、`config.py`、四个签名、异常体系、日志格式（**C 已整理好《接口公布说明》见 `C/接口公布说明.md`，含测试源站约定、`OriginClient` 用法、异常映射建议与给 A、B 的注意点，A 定稿时可直接参考**，避免方案与 C 现状脱节）；

## 三、A 的完成路线（proxy_server.py + 公共文件 + 集成）

按顺序执行：

1. **维护公共文件**：建立 `http_types.py` 权威版本与 `config.py`（端口 8888/8000、超时、请求头上限、线程池大小等），分发给 B、C；
2. **`read_client_request(sock)`**：循环 `recv` 直至收到完整首部（不假设一次收全），设置读取超时与请求头大小上限；仅支持 GET，其他方法返回 501；拒绝带请求体的 GET；产出 `HTTPRequest`；
3. **并发接入**：有限线程池 accept 连接，一个连接处理一个请求后关闭，响应带 `Connection: close`；
4. **调用 B**：将 `HTTPRequest` 交给 `CacheController.handle(request)`，拿回最终 `HTTPResponse`；
5. **`write_client_response(sock, response)`**：**输出前重新生成正确的 `Content-Length` 与 `Connection` 头**（不得透传源站首部），完整发送；
6. **错误响应映射**：捕获统一异常，映射为 400（请求非法）/502（源站连接失败、协议错误）/504（源站超时）；保证单次请求失败不终止服务；
7. **连接清理与日志**：异常分支也要关闭连接；日志带请求编号、URL、处理结果标记；
8. **模块测试**（架构文档指定重点）：请求分段到达、非法请求、并发连接、客户端提前断开、响应完整性；
9. **集成**：阶段 2 中把三人代码合并为根目录布局，提供启动入口（`python proxy_server.py --port 8888`），保证客户端可通过配置代理连接使用；
10. **配合联调**：与 B、C 跑通端到端，修复集成时出现的接入层问题。

**交付物**：`proxy_server.py`、`http_types.py`、`config.py`、对应模块测试、关键代码截图与注解、接入模块的架构说明文字。

## 四、B 的完成路线（cache_controller.py + cache_store.py）

按顺序执行：

1. **确认数据结构**：与 A 对齐 `CacheEntry`（缓存响应、请求/响应时间、初始年龄、新鲜期、ETag/Last-Modified、条目大小）；
2. **`cache_store.py` 存储层**：内存缓存 + 容量上限 + LRU 淘汰 + 条目大小统计；共享数据加锁；
3. **`CacheController.handle(request)` 决策树**：按顺序判断——是否绕过（带 `Authorization`/`Cookie`/`Range`/客户端条件头 → BYPASS，不查不存）→ 是否可保存（`Set-Cookie`/`Vary` → 不保存）→ 有缓存且新鲜（HIT，直接返回）→ 需验证（REVALIDATE）→ 无缓存（MISS）；
4. **新鲜度计算**：默认新鲜期为零；支持 `s-maxage`、`max-age`、`Expires`；计算考虑 `Date`、`Age`；缓存控制指令：`no-cache` 使用前验证、`no-store` 不存储、`private` 不进共享缓存；**过期不提供陈旧内容**；
5. **条件验证**：调用 C 前准备好条件首部——**ETag 优先（`If-None-Match`），其次 Last-Modified（`If-Modified-Since`）**，无验证标识则重新获取；**必须在缓存锁之外调用 `OriginClient.fetch`**（不持锁进行网络访问）；
6. **处理结果**：收到 304 → 复用本地缓存正文、刷新新鲜度、更新元数据；收到新 200 → 替换缓存正文；保存时按策略过滤；
7. **Age 维护**：缓存命中响应中的 `Age` 头由 B 计算并更新；
8. **模块测试**（架构文档指定重点）：命中与过期、缓存指令（no-cache/no-store/private）、304 更新、正文替换、LRU 淘汰、并发读写；
9. **日志**：按统一格式记录 HIT/MISS/REVALIDATE/BYPASS/UPDATE；
10. **报告职责**：撰写缓存策略与测试结果章节；阶段 4 负责**最终合并三人报告**，统一编号、术语、图注和排版。

**交付物**：`cache_controller.py`、`cache_store.py`、对应模块测试、缓存策略报告章节、合并后的完整实验报告。

## 五、C 的完成路线（origin_client.py + mock_origin_server.py + 抓包分析）

按顺序执行（✅ = 当前已完成）：

1. ✅ **`mock_origin_server.py` 可控测试源站**：端口 8000；`/index.html`（200 + Content-Length + Last-Modified/ETag/Cache-Control，条件命中返 304）、`/chunked`、`/eof`、`/update`、`/reset`、`/status`、`/delay`；
2. ✅ **`origin_client.py` 源站通信**：`fetch(request, conditional_headers=None)`；构造规范请求（补全 Host、`Connection: close`）；三种定界（Content-Length / chunked 解码 / EOF）；超时控制；异常分类抛出（超时→504 类、连接失败→502 类、协议错误→502 类）；
3. ✅ **模块测试**：12 项全部通过（三种定界、条件请求 304、更新后 200、超时、源站异常断开，以及分帧到达、Trailer、HEAD 无正文、重复首部保留、请求构造等健壮性场景）；
4. ✅ **《接口公布说明》（`C/接口公布说明.md`）**：已整理一页协作说明并可供 A、B 随时参考，内容含测试源站路径与首部约定、`OriginClient` 用法与异常映射建议、给 A 的注意点（错误响应由 A 合成、输出前重写首部、源站已支持并发）、给 B 的注意点（锁外调用、ETag 优先、304 复用正文、`max-age=10` 测 HIT）、待修订项清单——A 定阶段 0 方案、B 开发前请先读此文；
5. ⬜ **按阶段 0 结论修订**：增加响应体/响应头大小上限；日志纳入统一格式与请求编号；异常类型改用全组统一体系；删除主链路中的 502/504 响应合成（移为仅单测验证）；
6. ⬜ **`traffic_generator.py` 抓包触发**：5 大场景一键触发（首次拉取 / 本地命中 / 304 验证 / 内容更新 / 多客户端并发），用原始 socket 发包排除浏览器缓存干扰；
7. ⬜ **阶段 3 联合抓包（C 主导）**：Wireshark 选 loopback 网卡，过滤器 `http and (tcp.port == 8888 or tcp.port == 8000)`；分场景保存 `.pcapng`；对关键报文（条件请求头、源站 304、HIT 时段无源站流量等）**标注截图**；结合 HIT 日志撰写每场景流程描述；
8. ⬜ **阶段 4 报告抓包章节**：形成可直接放入报告的完整章节（接收请求、本地响应、拉取页面等流程描述），将 `.pcapng` 原始文件、标注截图、分析文字一并交 B 合并；
9. ⬜ **配合联调**：A、B 集成与端到端测试期间，负责源站侧问题修复与缓存状态控制（`/update`、`/reset`）。

**交付物**：`origin_client.py`、`mock_origin_server.py`、`traffic_generator.py`、模块测试、关键代码截图与注解、《接口公布说明》、5 个场景 `.pcapng` 原始文件 + 标注截图 + 分析文字、报告抓包章节。

## 六、联调与验收路线（阶段 2–3，共同）

1. **A 完成集成**：三人代码并入根目录，启动代理（8888）与测试源站（8000）；
2. **冒烟测试**：C 用 `traffic_generator.py` 逐场景触发，A 看接入日志、B 看缓存决策日志，确认 HIT/MISS/REVALIDATE/BYPASS 行为正确；
3. **5 场景端到端验收**（架构文档指定）：
   - 首次拉取（MISS）→ 本地响应（HIT，验证无源站流量）→ 过期 304 验证 → 源站更新后 200 → 多客户端并发（验证多 TCP 流无串流）；
4. **问题定位规则**：按模块归属修复（接入问题找 A、缓存决策找 B、源站通信找 C），整合期不改公共接口，确需改动先三方同步；
5. **抓包定稿**：C 在全部场景行为正确后正式抓包、标注、写分析文字。
